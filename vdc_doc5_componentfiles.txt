===component-alert.qml===  
  
{{code|component-alert.qml}} implements the shared modal dialog component used throughout the Black Mesa Qt UI. It is registered in {{code|qmldir}} as {{code|Alert 1.0}} and is instantiated directly by eight files: {{code|routeview-quit.qml}}, {{code|routeview-savebeforequit.qml}}, {{code|routeview-savegame.qml}}, {{code|routeview-loadgame.qml}}, {{code|routeview-video.qml}}, {{code|routeview-audio.qml}}, {{code|routeview-bindings.qml}}, and {{code|main.qml}}.

====Root Element====  
  
The root element is a {{code|MouseArea}}, not an {{code|Item}} or {{code|Rectangle}}. This is intentional: the {{code|MouseArea}} fills its parent ({{code|anchors.fill: parent}}) and intercepts all pointer events, preventing click-through to the content behind the modal while it is visible. {{code|hoverEnabled: true}} is set so that {{code|onEntered}} and {{code|onExited}} handlers can also consume hover events. Both handlers are empty stubs whose sole purpose is event interception. {{code|onClicked}} calls {{code|mouse.accepted [[=]] true}} for the same reason.  
  
The root starts with {{code|visible: false}} and {{code|state: "hidden"}}. The {{code|enabled}} and {{code|hoverEnabled}} properties are toggled by the state machine rather than being hardcoded.

====Public API====  
  
Two functions control the modal's visibility:  
  
* {{code|show()}} — sets {{code|state [[=]] "visible"}}, triggering the show transition.  
* {{code|hide()}} — sets {{code|state [[=]] "hidden"}}, triggering the hide transition.  
  
There are no signals. Consumers communicate results entirely through button {{code|onClicked}} handlers defined inline in the {{code|VisualItemModel}}.

====Visual Structure====  
  
=====Skrim=====  
  
{{code|skrimRect}} is a full-parent {{code|Rectangle}} with {{code|color: Theme.colors.skrim}} ({{code|#2d2d2d}}) and {{code|visible: skrim}}. When {{code|skrim}} is {{code|false}}, the rectangle is hidden entirely regardless of opacity. Two consumers — {{code|routeview-quit.qml}} and {{code|routeview-savebeforequit.qml}} — set {{code|skrim: false}} because they are full-screen route views with their own background, not overlays on top of other content.  
  
=====Modal Panel=====  
  
{{code|modal}} is an {{code|Item}} centered in the root via {{code|anchors.centerIn: parent}}. Its initial {{code|anchors.verticalCenterOffset}} is {{code|30000}}, placing it far off-screen. The show/hide transitions animate this offset to move the panel on and off screen.  
  
The panel contains three child elements stacked vertically:  
  
1. '''Header bar''' ({{code|header}}): an {{code|Item}} of height {{code|alert.headerHeight}} containing a {{code|Rectangle}} filled with {{code|Theme.colors.highlight}} ({{code|#e47125}}) at {{code|opacity: Theme.opacity.modalHeader}} (0.85), and a {{code|Text}} element ({{code|headerText}}) with {{code|Font.AllUppercase}} capitalization, {{code|Theme.fonts.bold}}, and {{code|color: Theme.colors.headerText}} (white).  
  
2. '''Body text''' ({{code|bodyText}}): a {{code|Text}} element anchored below the header with {{code|anchors.topMargin: alert.padding}}. Uses {{code|Theme.fonts.light}}, {{code|color: Theme.colors.text}} (white), and {{code|textFormat: Text.RichText}}. No explicit width is set.  
  
3. '''Button row''': a horizontal {{code|ListView}} anchored below {{code|bodyText}} with {{code|layoutDirection: Qt.RightToLeft}}, {{code|height: headerHeight}}, {{code|interactive: false}}, and {{code|cacheBuffer: 0}}. Its {{code|model}} is the {{code|buttons}} {{code|VisualItemModel}} property. Buttons are right-aligned and laid out right-to-left, so the first item in the model appears rightmost.  
  
A {{code|background}} {{code|Rectangle}} fills the entire {{code|modal}} panel with {{code|color: Theme.colors.modalBackground}} ({{code|#222222}}) and {{code|opacity: Theme.opacity.modal}} (0.95).

====Transitions====  
  
=====Show (hidden → visible)=====  
  
A {{code|ParallelAnimation}} runs three animations simultaneously:  
  
# {{code|skrimRect.opacity}} animates to its target value over 600 ms (no easing specified, defaults to linear).  
# {{code|modal.anchors.verticalCenterOffset}} animates from 300 to 0 over 600 ms with {{code|Easing.InOutQuint}}.  
# A {{code|SequentialAnimation}}:  
## {{code|ScriptAction}}: calls {{code|BlackMesaUtils.clearUIElementsData()}}.  
## {{code|PauseAnimation}}: 300 ms.  
## {{code|NumberAnimation}}: {{code|modal.opacity}} from 0.0 to 1.0 over 300 ms.  
## {{code|PauseAnimation}}: 150 ms.  
## {{code|ScriptAction}}: calls {{code|BlackMesaUtils.traverseUIElements(alert)}} then {{code|BlackMesaUtils.afterTraverseCallback()}} to register the modal's interactive elements with the controller/keyboard navigation system.  
  
=====Hide (catch-all)=====  
  
The second {{code|Transition}} has no {{code|from}} or {{code|to}} attributes, making it the catch-all for all other state changes (in practice, {{code|visible → hidden}}). It runs a {{code|SequentialAnimation}}:  
  
# {{code|ScriptAction}}: calls {{code|BlackMesaUtils.clearUIElementsData()}}.  
# {{code|ParallelAnimation}}:  
## {{code|skrimRect.opacity}} to 0 over 600 ms.  
## {{code|modal.anchors.verticalCenterOffset}} from 0 to 300 over 600 ms with {{code|Easing.InOutQuint}}.  
## {{code|modal.opacity}} from 1.0 to 0.0 over 300 ms.  
# {{code|NumberAnimation}}: {{code|modal.anchors.verticalCenterOffset}} from 300 to 30000 over 1 ms — an instant snap to the off-screen parking position.  
# {{code|ScriptAction}}: calls {{code|BlackMesaUtils.traverseUIElements(appRoot)}}, {{code|BlackMesaUtils.afterTraverseCallback()}}, and {{code|appRoot.forceActiveFocus()}} to restore navigation focus to the main UI.

====Notable Issues====  
  
1. '''{{code|modalWidth}} uses {{code|Theme.heightScale}}.''' The width is computed as <code><nowiki>Math.ceil(700 * Theme.heightScale)</nowiki></code> instead of {{code|Theme.widthScale}}. On non-square displays where the two scale factors differ, the modal will be narrower or wider than intended relative to the horizontal layout.  
  
2. '''{{code|spacing}} property is dead code.''' The property <code><nowiki>spacing: Math.ceil(25 * Theme.heightScale)</nowiki></code> is declared but referenced nowhere in the component's layout. No child element uses it.  
  
3. '''{{code|bodyText}} has no explicit width.''' The body {{code|Text}} element has no {{code|width}} binding. If {{code|messageText}} is a long single-line string, it will overflow the modal panel horizontally with no clipping, since {{code|modal}} does not set {{code|clip: true}}.  
  
4. '''Double opacity on the background rectangle.''' The {{code|background}} {{code|Rectangle}} inside {{code|modal}} has {{code|opacity: Theme.opacity.modal}} (0.95) hardcoded. The parent {{code|modal}} {{code|Item}} also has its {{code|opacity}} animated from 0 to 1 during the show transition. The effective background opacity when fully visible is <code><nowiki>0.95 × 0.95 ≈ 0.9025</nowiki></code>, not 0.95 as intended. The header and body text are children of {{code|modal}} and are also subject to the parent opacity, so they are unaffected by the background's own opacity setting.  

5. '''{{code|modal.anchors.verticalCenterOffset: 30000}} is an off-screen parking hack.''' The modal is hidden by moving it 30,000 pixels below center rather than by setting {{code|visible: false}}. This is necessary because QML transitions cannot run on elements with {{code|visible: false}}. The 1 ms {{code|NumberAnimation}} at the end of the hide transition snaps the offset back to 30000 after the slide-out animation completes, ensuring the modal is parked off-screen before the next show.  
  
6. '''Catch-all hide transition.''' The second {{code|Transition}} has no {{code|from}} or {{code|to}} specified, making it apply to all state changes not matched by the first transition. Since there are only two states ({{code|hidden}} and {{code|visible}}), this is equivalent to specifying <code><nowiki>from: "visible"; to: "hidden"</nowiki></code>, but it is less explicit and would silently apply to any future states added to the component.  
  
7. '''{{code|appRoot}} referenced by id in the hide transition.''' The {{code|ScriptAction}} at the end of the hide transition calls {{code|BlackMesaUtils.traverseUIElements(appRoot)}} and {{code|appRoot.forceActiveFocus()}}. {{code|appRoot}} is the root {{code|Item}} id defined in {{code|main.qml}}. This creates an implicit dependency on the id being in scope at the point where {{code|Alert}} is instantiated. All current consumers are direct or indirect children of {{code|appRoot}}, so this works, but it makes {{code|Alert}} non-portable outside of the {{code|main.qml}} hierarchy.  
  
8. '''{{code|routeview-quit.qml}} and {{code|routeview-savebeforequit.qml}} auto-show on {{code|Component.onCompleted}}.''' These two consumers call {{code|alert.show()}} immediately when the component is created, meaning the modal appears as soon as the route is pushed onto the {{code|StackView}}. The show transition (600 ms) runs concurrently with the router's push transition, which may produce visual overlap between the two animations.  
  
9. '''Button order is right-to-left.''' The {{code|ListView}} uses {{code|layoutDirection: Qt.RightToLeft}}, so the first item in the {{code|VisualItemModel}} appears at the rightmost position. Consumers must account for this when ordering buttons: the primary action (e.g. Quit, Apply) is placed first in the model to appear on the right, and Cancel is placed last to appear on the left.

===component-binding.qml===

It is registered in {{code|qmldir}} as {{code|BindingList 1.0 component-binding.qml}} and is subclassed by {{code|component-binding-movement.qml}}, {{code|component-binding-combat.qml}}, {{code|component-binding-misc.qml}}, {{code|component-binding-weapons.qml}}, and {{code|component-binding-multiplayer.qml}}.  
  
====Overview====

====Functions====  
  
=====refreshBindings()=====  
  
Defers a call to {{code|InputBindingsManager.getBindings()}} by 1 ms using the internal {{code|timer.setTimeout()}} helper. Extracts the command strings from the {{code|commands}} array, passes them to {{code|getBindings()}}, and stores the result in {{code|bindings}}. The 1 ms deferral prevents synchronous blocking during binding-change events.  
  
<code><nowiki>var keys = commands.map(function (cfg) { return cfg.command; });  
InputBindingsManager.getBindings(keys, function (response) { bindings = response; });</nowiki></code>  
  
====Internal Timer====  
  
A {{code|Timer}} element with {{code|id: timer}} implements a {{code|setTimeout(callback, delay)}} helper. It stops any running timer, sets the interval, connects the callback and a self-disconnecting release function to {{code|triggered}}, then starts. This pattern ensures only one deferred call is pending at a time; a second call to {{code|setTimeout}} before the first fires will cancel the first.  
  
====Connections to InputBindingsManager====  
  
A {{code|Connections}} block targets the {{code|InputBindingsManager}} singleton and calls {{code|refreshBindings()}} on three signals:  
  
{| class="standard-table"  
! Signal  
! Trigger  
|-  
| {{code|onBindingSet}}  
| A key was successfully bound to a command.  
|-  
| {{code|onBindingClear}}  
| A binding was cleared.  
|-  
| {{code|onDefaultsRestored}}  
| All bindings were reset to defaults.  
|}  
  
{{code|Component.onCompleted}} also calls {{code|refreshBindings()}} to populate the initial state.  
  
====onBindingsChanged Handler====  
  
When {{code|bindings}} is updated, the handler iterates over every item in {{code|bindingsList.model}}, resets {{code|key1}} and {{code|key2}} to empty strings, then repopulates them from the new {{code|bindings}} map:  
  
<code><nowiki>current.key1 = bindings[current.command][0];  
current.key2 = bindings[current.command][1];</nowiki></code>  
  
This directly mutates {{code|ListModel}} role properties in-place. The {{code|ListModel}} must have been populated with {{code|key1}} and {{code|key2}} roles at {{code|append()}} time for this to work; if a role is absent, the assignment silently fails.

The model is a {{code|ListModel}} populated in {{code|Component.onCompleted}} by iterating over {{code|commands}} and calling {{code|append(cfg)}} for each config object. Each {{code|cfg}} object has the roles {{code|label}}, {{code|type}}, {{code|command}}, {{code|key1}}, and {{code|key2}}.  
  
=====Delegate=====  
  
Each row is a {{code|Loader}} with {{code|width: bindingsList.width}} and {{code|height: rowHeight}}. In {{code|Component.onCompleted}}, the loader calls:  
  
<code><nowiki>loader.setSource('component-optionslist-row.qml', { model: model, selected: selected })</nowiki></code>  
  
The {{code|model}} passed is the {{code|ListModel}} role object for that row. The {{code|selected}} value is the {{code|BindingList}}-level {{code|selected}} property, shared identically across all rows.  
  
=====Inline ScrollBar=====  
  
The {{code|ListView}} attaches an inline {{code|ScrollBar}} via {{code|ScrollBar.vertical}} rather than using the registered {{code|VerticalScrollBar}} type. Visibility is conditional:  
  
<code><nowiki>visible: bindingsList.height + bindingsList.bottomMargin + bindingsList.topMargin + 2 < bindingsList.contentHeight</nowiki></code>  
  
The thumb is a {{code|Rectangle}} with {{code|implicitWidth: scrollbarDimension}} and {{code|color: Theme.colors.highlight}}.

====Quirks and Observations====  
  
1. '''Both declared signals are dead code.''' {{code|requestInputBinding}} and {{code|requestInputSelection}} are never emitted anywhere in the file or in any subclass. The actual binding-capture flow bypasses these signals entirely, going directly through {{code|InputBindingsManager.selectBinding()}} and {{code|InputBindingsManager.startBindingRequest()}} from {{code|component-optionslist-input-bindingcell.qml}}.  
  
2. '''Inline {{code|ScrollBar}} duplicates {{code|VerticalScrollBar}}.''' The registered {{code|VerticalScrollBar 1.0}} type is not used here. The inline scrollbar uses {{code|scrollbarDimension}} based on {{code|Theme.widthScale}}, while {{code|VerticalScrollBar}} uses {{code|Theme.widthScale}} as well but is a separate, independently maintained implementation. Any future changes to the scrollbar style must be applied in both places.  
  
3. '''{{code|cacheBuffer: 50000}} pre-renders all rows.''' With {{code|rowHeight}} of approximately 85 scaled pixels, a list of 15 rows (the maximum in {{code|component-binding-weapons.qml}}) has a total height of roughly 1275 scaled pixels. A cache buffer of 50000 pixels ensures every row is always instantiated, effectively disabling ListView's virtualization for this component.  
  
4. '''{{code|selected}} is a single value shared by all rows.''' The {{code|selected}} property on the {{code|BindingList}} root is passed identically to every row delegate. It is not per-row; it reflects the global selection state managed by {{code|InputBindingsManager.selectedCfg}}. Individual row selection is handled inside {{code|component-optionslist-input-bindingcell.qml}} by comparing {{code|InputBindingsManager.selectedCfg}} to the row's own config.  
  
5. '''{{code|onBindingsChanged}} resets all rows on every binding change.''' Even if only one binding changed (e.g. a single key was rebound), the handler clears and repopulates {{code|key1}} and {{code|key2}} for every row in the model. For the largest category (weapons, 15 rows) this is 15 model mutations per binding event.  
  
6. '''No {{code|id}} on the root {{code|Item}}.''' Consistent with all other {{code|component-binding-*.qml}} files, but means child elements cannot reference the root by id.  
  
7. '''{{code|timer.setTimeout}} cancels any pending deferred call.''' If {{code|refreshBindings()}} is called twice in rapid succession (e.g. {{code|onBindingSet}} fires while a previous refresh is still pending), the second call cancels the first. This is intentional but means the first callback is silently dropped without executing.

====Function: changePagination(type)====  
  
The sole public function. Advances or retreats the carousel by one page. It is a no-op if {{code|paginateAnimSeq.running}} is {{code|true}} (i.e., a pagination animation is already in progress).  
  
Parameters:  
* {{code|type [[=]] -1}} — scroll left (backward) by {{code|visibleCount}} items.  
* {{code|type [[=]] 1}} — scroll right (forward) by {{code|visibleCount}} items.  
  
=====Left pagination (type = -1)=====  
  
# Computes <code><nowiki>leftIndex = Math.floor(currX / itemW)</nowiki></code> where {{code|itemW [[=]] carousel.itemWidth}}.  
# Computes <code><nowiki>newIndex = leftIndex - visibleCount >= 0 ? leftIndex - visibleCount : 0</nowiki></code>.  
# Calls <code><nowiki>itemsList.positionViewAtIndex(newIndex, ListView.Beginning)</nowiki></code> to snap {{code|contentX}} to the target position, then reads back the new {{code|contentX}} as the animation target.  
# Starts {{code|paginateAnimSeq}} to animate {{code|contentX}} from the old to the new value.  
# Updates {{code|showRight}} based on whether items remain beyond the new right edge.  
# Sets {{code|showLeft [[=]] false}} if {{code|newIndex [[=]][[=]] 0}}.

=====Right pagination (type = 1)=====  
  
# Computes <code><nowiki>rightIndex = leftIndex + visibleCount - 1</nowiki></code>.  
# Computes <code><nowiki>clippedRightCount = count - (visibleCount + leftIndex)</nowiki></code>.  
# Computes <code><nowiki>newIndex = clippedRightCount - visibleCount >= 0 ? rightIndex + visibleCount : count - 1</nowiki></code>.  
# Calls <code><nowiki>itemsList.positionViewAtIndex(newIndex, ListView.End)</nowiki></code>.  
# Starts {{code|paginateAnimSeq}}.  
# Updates {{code|showLeft}} based on whether {{code|newIndex - visibleCount >[[=]] 0}}.  
# Sets {{code|showRight [[=]] false}} if {{code|newIndex [[=]][[=]] count - 1}}.

====Observations====  
  
1. '''{{code|showRight}} initialization uses a hardcoded literal 4.''' In {{code|Component.onCompleted}}, <code><nowiki>showRight = count > 4</nowiki></code> uses the literal {{code|4}} instead of {{code|visibleCount}}. On a display where {{code|visibleCount}} computes to a value other than 4 (e.g. a very wide or narrow window), the initial arrow visibility will be incorrect. Consumers that repopulate {{code|levels}} after construction ({{code|routeview-newgame.qml}}, {{code|routeview-addons.qml}}) work around this by setting {{code|showRight}} explicitly in their {{code|onCurrentlySelectedCampaignChanged}} handler, but {{code|routeview-loadgame.qml}} and {{code|routeview-savegame.qml}} do not, leaving them exposed to this bug.  
  
2. '''{{code|itemHeight}} is declared but never used.''' The property is defined as <code><nowiki>Math.ceil(400 * Theme.heightScale)</nowiki></code> but is not referenced anywhere inside {{code|component-carousel.qml}}. The {{code|mask}} height uses {{code|maskHeight}} (which has the same formula), and the {{code|ListView}} height is {{code|parent.height}}. {{code|itemHeight}} is also not read by any consumer. It is dead code.  
  
3. '''{{code|leftIndex}} calculation ignores {{code|itemSpacing}}.''' {{code|changePagination}} computes <code><nowiki>leftIndex = Math.floor(currX / itemW)</nowiki></code> where {{code|itemW [[=]] carousel.itemWidth}}. The correct stride per item is <code><nowiki>itemWidth + itemSpacing</nowiki></code>. Because {{code|positionViewAtIndex}} always sets {{code|contentX}} to a multiple of the true stride, the fractional error is <code><nowiki>n * itemSpacing / itemWidth</nowiki></code> per page. With the default values ({{code|itemWidth [[=]] 400}}, {{code|itemSpacing [[=]] 8}}), the error reaches 1.0 at {{code|n [[=]] 50}} pages, at which point {{code|Math.floor}} produces an incorrect {{code|leftIndex}}. This is a latent bug that does not manifest in practice given typical save/chapter counts.  
  
4. '''{{code|itemsList.limit}}, {{code|offset}}, and {{code|page}} are dead code.''' These three properties are declared on the {{code|ListView}} but are never read or written by any code path in the file or by any consumer. They are remnants of an earlier offset-based pagination design.  
  
5. '''{{code|cacheBuffer: 8000}} is not scaled.''' The {{code|ListView}} pre-renders items within 8000 pixels of the visible area. This value is not multiplied by {{code|Theme.widthScale}}, so on high-DPI or scaled displays the effective cache coverage in logical units will differ from the intended amount.  
  
6. '''{{code|CarouselButton.buttonHeight}} uses {{code|Theme.widthScale}}.''' The button height formula is <code><nowiki>Math.ceil(214 * Theme.widthScale)</nowiki></code>. Using {{code|widthScale}} for a vertical dimension is inconsistent with the convention used throughout the rest of the UI, where {{code|Theme.heightScale}} governs vertical sizes.  
  
7. '''Post-pagination {{code|ScriptAction}} re-traverses the entire UI tree.''' After every page turn, {{code|BlackMesaUtils.parseTraversalTree(appRoot)}} walks the full component tree from the root to rebuild the controller navigation graph. This is an O(n) operation over all UI elements and is called synchronously in the animation completion callback. On complex pages this may introduce a perceptible hitch at the end of the scroll animation.  
  
8. '''{{code|var newIndex}} is declared twice in the same function scope.''' {{code|changePagination}} uses {{code|var newIndex}} in both the {{code|type [[=]][[=]] -1}} and {{code|type [[=]][[=]] 1}} branches. JavaScript {{code|var}} is function-scoped, so the second declaration is a silent re-declaration of the same variable. This is valid ES5 but is a code smell; {{code|let}} would scope each declaration to its block.

====Navigation Integration====  
  
{{code|BlackMesaUtils.traverseUIElements()}} in {{code|utils.qml}} detects items with <code><nowiki>objectName === "ui:carousel-item"</nowiki></code> and adds them to the {{code|optionItems}} array. After traversal, {{code|afterTraverseCallback()}} sets the initial focus to {{code|optionItems[0]}} and calls {{code|updateCurrentUISelection()}}, which calls {{code|forceActiveFocus()}} on the item.  
  
{{code|processCarouselItemSelection(sign)}} in {{code|utils.qml}} handles left/right keyboard navigation between carousel items. It also triggers pagination by directly calling {{code|clicked(null)}} on the left or right {{code|CarouselButton}} when the index crosses a page boundary. The boundary detection uses <code><nowiki>previousIndex % 4</nowiki></code> and <code><nowiki>optionItemIndex % 4</nowiki></code>, hardcoding an assumption of 4 items per page.  
  
On {{code|Qt.Key_Enter}}, {{code|navigationUIHandle()}} calls {{code|currentElement.selected()}} directly on the focused carousel item, bypassing the button's {{code|clicked}} signal.

====Notable Issues====  
  
1. '''{{code|thumbnailHeight}} and {{code|thumbnailWidth}} are dead properties.''' Both are declared and scaled but never referenced. The actual thumbnail dimensions are determined by {{code|anchors.fill}} and the <code><nowiki>Math.floor(width * 0.56)</nowiki></code> height formula.  
  
2. '''{{code|thumbnailBottomMargin}} has no effect.''' It is assigned to {{code|anchors.bottomMargin}} on {{code|thumbnailContainer}}, but {{code|thumbnailContainer}} has no bottom anchor, so the margin is never applied.  
  
3. '''{{code|background.border.width: 1}} is not scaled.''' All other dimension properties use {{code|Theme.widthScale}} or {{code|Theme.heightScale}}, but the card border is a hardcoded 1px and will appear proportionally thinner at higher resolutions.  
  
4. '''Both buttons load the same {{code|buttonType}}.''' {{code|loaderSecondary}} uses <code><nowiki>"button-" + buttonType + ".qml"</nowiki></code>, identical to {{code|loader}}. In {{code|routeview-savegame.qml}}, existing-save cards have {{code|buttonType: "warning"}}, so both the Overwrite and Delete buttons are rendered as {{code|WarningButton}}.  
  
5. '''{{code|buttonType}} is an unvalidated string.''' A typo (e.g. {{code|"cta "}} with a trailing space) causes {{code|setSource()}} to silently fail to load the button, leaving the card with no action button and no error output.  
  
6. '''{{code|selectedWithDoubleClick}} is universally aliased to {{code|selected()}}.''' Every consumer's {{code|onSelectedWithDoubleClick}} handler calls {{code|selected()}} with no distinction. The signal is effectively unused as a separate interaction.  
  
7. '''{{code|when:}} conditions on {{code|blurred}} and {{code|focused}} reference {{code|carouselItem.activeFocus}}, but hover overrides them.''' {{code|onEntered}} and {{code|onExited}} set the state explicitly, bypassing the {{code|when:}} bindings. If the item gains {{code|activeFocus}} via keyboard navigation while the mouse is hovering over a different item, the {{code|when:}} condition for {{code|focused}} will be true but the explicit {{code|"blurred"}} set by {{code|onEntered}} on the hovered item takes precedence. The commented-out conditions (<code><nowiki>// || loader.item.activeFocus || loaderSecondary.item.activeFocus</nowiki></code>) suggest button-level focus was intended to also trigger the focused state but was disabled.  
  
8. '''{{code|processCarouselItemSelection}} hardcodes modulo 4 for page boundary detection.''' The pagination trigger logic uses <code><nowiki>previousIndex % 4</nowiki></code> and <code><nowiki>optionItemIndex % 4</nowiki></code>. At resolutions where {{code|visibleCount}} is not 4 (e.g. narrower windows), the pagination arrows will be triggered at the wrong index boundaries.  
  
9. '''{{code|propagateComposedEvents: true}} on the {{code|MouseArea}}.''' Composed events (e.g. clicks) propagate to parent items. In the {{code|ListView}} → {{code|Carousel}} hierarchy, this is unlikely to cause issues since the {{code|ListView}} has {{code|interactive: false}}, but it is an unintentional permissiveness.

====Notable issues====

2. '''{{code|chapterNameFontSize}} uses {{code|Theme.widthScale}}, {{code|dateFontSize}} uses {{code|Theme.heightScale}}.''' The two font sizes scale on different axes. 4. '''{{code|onSelected}} and {{code|onSelectedWithDoubleClick}} are identical in both consumers.''' Single-click and double-click produce the same result with no distinction in behaviour.

6. '''{{code|verticalSpacing}} shadows the base class property.''' {{code|CarouselItem}} also declares a {{code|verticalSpacing}} property (defaulting to <code><nowiki>Math.ceil(10 * Theme.heightScale)</nowiki></code>) used for thumbnail and button padding. {{code|CarouselLoadGameItem}} redeclares it as <code><nowiki>Math.ceil(2 * Theme.heightScale)</nowiki></code>. Structurally identical to {{code|routeview-newgame.qml}} but filters campaigns with <code><nowiki>!campaign.isOfficial</nowiki></code>. Displays a fallback {{code|Text}} element with {{code|#BlackMesaUI_WorkshopList_Empty}} when {{code|levels.count [[=]] 0}}.  
  
====Notable issues====  
  
1. '''{{code|verticalSpacing}} override affects base class layout.''' The base class uses {{code|verticalSpacing}} for both the content area padding ({{code|anchors.rightMargin}}, {{code|anchors.leftMargin}}, {{code|anchors.topMargin}}) and the button bottom/left margins. Overriding it to {{code|2}} in {{code|CarouselNewGameItem}} reduces all of these paddings from 10 px (scaled) to 2 px (scaled), not just the {{code|Column}} spacing. This is a side effect of the base class reusing a single property for multiple layout roles.  
  
2. '''Mixed scaling axes on font sizes.''' {{code|chapterNameFontSize}} scales by {{code|Theme.widthScale}} while {{code|numberFontSize}} scales by {{code|Theme.heightScale}}. On non-16:9 displays where the two scale factors differ, the two text lines will scale at different rates.  
  
3. '''Both text colors are identical.''' {{code|chapterNameText}} uses {{code|Theme.colors.headerText}} and {{code|chapterNumberText}} uses {{code|Theme.colors.text}}. Both resolve to {{code|white}}. There is no visual color differentiation between the primary and secondary text lines.  
  
4. '''{{code|type}} default is always overridden.''' The default value <code><nowiki>BlackMesaEngine.getLocalizedString("#GameUI_Chapter")</nowiki></code> is evaluated at construction time but is immediately replaced by both consumers. The evaluation is wasted.  
  
5. '''{{code|isLocked}} is always {{code|false}}.''' The lock mechanism in the base class (lock icon, disabled mouse area, hidden text) is fully implemented but never activated. The chapter-locking logic based on {{command|sv_unlockedchapters}} is commented out in {{code|routeview-newgame.qml}}.  
  
6. '''{{code|onSelectedWithDoubleClick: selected()}} in both consumers.''' Double-click and single-click produce identical behaviour. The {{code|selectedWithDoubleClick}} signal from the base class is never used distinctly.  
  
7. '''{{code|thumbnailHeight}} and {{code|thumbnailWidth}} are dead properties.''' The base class declares these but the thumbnail container uses <code><nowiki>height: Math.floor(width * 0.56)</nowiki></code> for its dimensions. Neither property is referenced anywhere in the layout.  
  
8. '''Secondary button is never shown.''' {{code|secondaryButtonVisible}} defaults to {{code|false}} and is never set to {{code|true}} by any consumer of {{code|CarouselNewGameItem}}. The {{code|loaderSecondary}} in the base class is always hidden.

# Executes the command via {{code|BlackMesaEngine.executeClientCommandUnrestricted(text)}}.

=====Keys.onTabPressed=====

# Sets {{code|event.accepted [[=]] true}} to suppress focus traversal.  
# Returns immediately if the field is empty.  
# Normalizes whitespace: <code><nowiki>text.replace(/\s+/g, " ")</nowiki></code>.  
# If {{code|storedAutocompleteIndex < 0}} (first Tab press in this cycle):  
## If the input contains a space, splits into a prefix (command name + space) and a search string (argument). Calls {{code|BlackMesaEngine.listConsoleSuggestions(prefix, search)}} to get argument completions.  
## If no space, calls {{code|BlackMesaEngine.listConsoleAutocompleteEntries(search)}} to get command completions.  
## Prints {{code|"] " + inputString}} to the console output.  
## If no suggestions, returns.  
## Sets {{code|storedAutocompleteIndex [[=]] 0}} and prints all suggestions tab-separated to the console output.  
# Sets {{code|commandField.text}} to {{code|prefix + autocompleteList[storedAutocompleteIndex]}}.  
# Calls {{code|select(searchString.length, text.length)}} to highlight the completed portion.  
# Increments {{code|storedAutocompleteIndex}}, wrapping to {{code|0}} at the end of the list.

====Notable observations====  
  
1. '''{{code|visible}} threshold is {{code|0.0009765625}}.''' This value is <code><nowiki>1/1024</nowiki></code>. It avoids the overhead of rendering and hit-testing a fully transparent item during the closed state, while still allowing the opacity animation to complete before the item is hidden.  
  
2. '''{{code|clear}} is handled specially.''' When the user submits {{code|"clear"}}, the echo step is skipped so the word {{code|"clear"}} does not appear in the output before {{code|outputModel.clear()}} is called by the engine's {{code|onGameConsoleCleared}} signal. However, the clear is not performed directly by QML — it depends on the engine firing {{code|onGameConsoleCleared}} in response to the command. If the engine does not fire that signal, the output is not cleared.  
  
3. '''History mutation requires self-reassignment.''' {{code|history.entries.push(text)}} is followed by {{code|history.entries [[=]] history.entries}} to trigger QML's property change notification. This is a standard QML workaround for in-place array mutation.  
  
4. '''{{code|outputView}} delegate uses {{code|TextField}}, not {{code|Text}}.''' Using {{code|TextField}} for read-only output lines allows the user to select and copy text from the console output. However, {{code|TextField}} is significantly heavier than {{code|Text}}; each console line creates a full {{code|TextField}} instance. Long sessions with many output lines will accumulate a large number of live {{code|TextField}} objects, since {{code|ListView}} does not recycle delegates when {{code|boundsBehavior: Flickable.StopAtBounds}} is set and the list is not virtualized beyond the visible area.  
  
5. '''No maximum history or output size.''' Both {{code|history.entries}} and {{code|outputModel}} grow unboundedly. The only way to clear {{code|outputModel}} is via the engine's {{code|onGameConsoleCleared}} signal (triggered by the {{code|clear}} command). {{code|history.entries}} is never trimmed.  
  
6. '''{{code|selectionColor}} equals {{code|color}}.''' The selection highlight background ({{code|selectionColor}}) is set to the same value as the text color ({{code|Theme.devConsole.colors.inputText}}, {{code|#ffd0d0d0}}). The selection is still visible because {{code|selectedTextColor}} is set to the dark background color, inverting the text. The highlight rectangle itself is light gray on a light gray background, which is semantically odd but functionally acceptable.  
  
7. '''Height is not {{code|Theme}}-scaled.''' The {{code|height: parent.height * 0.375}} expression uses a raw proportion of the parent height rather than a {{code|Theme.heightScale}}-based calculation. This is consistent with the console being a fixed-proportion overlay rather than a layout-managed component, but it means the console height does not respond to the same scaling system as all other UI elements.

====Notable quirks and issues====  
  
1. '''{{code|isInGame}} binding is broken by direct assignment.''' {{code|main.qml}} declares <code><nowiki>isInGame: appRoot.isInGame</nowiki></code> as a binding, but then directly assigns {{code|footer.isInGame}} in {{code|onLevelLoadingFinished}} and {{code|onDisconnectedFromServer}}. In QML, a direct property assignment destroys the declarative binding. After the first level load completes, {{code|footer.isInGame}} is no longer reactive to {{code|appRoot.isInGame}} changes.  
  
2. '''Loading font sizes use {{code|Theme.widthScale}} instead of {{code|Theme.heightScale}}.''' {{code|loadingLabelFontSize}} and {{code|levelNameFontSize}} are scaled by {{code|Theme.widthScale}}, while {{code|loadingQuoteFontSize}}, {{code|progressBarHeight}}, and {{code|levelNameMarginBottom}} use {{code|Theme.heightScale}}. On non-16:9 displays where the two scales differ, the level name and "Loading Level" label will be disproportionately sized relative to the progress bar and quote text.  
  
3. '''Progress bar floats outside the footer's own bounds.''' The {{code|progressBar}} item uses {{code|anchors.bottom: parent.top}}, placing it above the footer rectangle and into the router's layout area. This is intentional (the bar appears as an overlay above the footer), but it means the progress bar is not clipped by the footer and could overlap route content during loading.  
  
4. '''{{code|MenuNavGuide}} anchor inside a {{code|Row}} is invalid.''' The {{code|MenuNavGuide}} instance sets <code><nowiki>anchors.right: discordLinkItem.left</nowiki></code>, but it is a child of a {{code|Row}} layout. {{code|Row}} manages its children's horizontal positions; anchor constraints on children of a {{code|Row}} are ignored by the layout engine. The guide will be positioned by the {{code|Row}}'s flow, not by the anchor.  
  
5. '''{{code|discordLinkItem}} uses {{code|anchors.right: parent.right}} inside a {{code|Row}}.''' Same issue as above — the anchor is ignored. The item will be placed at the end of the {{code|Row}}'s flow, which happens to produce the correct visual result, but only incidentally.  
  
6. '''{{code|showLoadingProgress: !appRoot._isInitialLoad}} hides the progress bar during the first load.''' During the initial main menu background load, the progress bar and quotes are suppressed and the "Loading Level" label is shown instead. This is intentional (the initial load is not a user-initiated action), but the logic is inverted from what the property name suggests — {{code|showLoadingProgress: false}} shows the "Loading Level" label, not nothing.  
  
7. '''Quote timer has a latent infinite loop.''' The {{code|while}} loop that prevents repeating the same quote will spin forever if {{code|quotes.length [[=]][[=]] 1}}. The source contains a TODO comment acknowledging this. With the current 5-quote pool this is not a problem, but adding or removing quotes without fixing the loop is a latent risk.  
  
8. '''No {{code|id}} on the {{code|loadingFooter}} root {{code|Item}}.''' Child elements inside {{code|loadingFooter}} cannot reference the root by id. The {{code|Timer}} accesses {{code|loadingQuoteText}} by id directly, which works via implicit QML scope but is fragile.

====Notable Observations / Bugs====  
  
1. '''{{code|multiplayerNavModel.Component.onCompleted}} executes a console command.''' The model's initializer calls <code><nowiki>BlackMesaEngine.executeClientCommandUnrestricted("exec server.cfg;")</nowiki></code>. This is a side effect embedded in a data model: {{code|server.cfg}} is executed every time the multiplayer sub-nav model is created, which happens at startup regardless of whether the user ever visits the multiplayer section.  
  
2. '''{{code|setState()}} is not called from {{code|Component.onCompleted}}.''' The initial state is hardcoded as {{code|"hidden"}} on the root element. If {{code|currentRoute}} or {{code|hide}} were set before the component finishes loading, {{code|setState()}} would not be triggered and the header could display in the wrong state. In practice {{code|main.qml}} sets {{code|hide}} after construction, which triggers {{code|onHideChanged}} and corrects the state.  
  
3. '''Sub-nav {{code|ListView}} is anchored to {{code|subNavContainer.verticalCenter}}.''' The {{code|anchors.top}} of the sub-nav list is bound to {{code|subNavContainer.verticalCenter}}, so the tabs only occupy the lower half of the 128-scaled-px sub-nav bar. The upper half is empty background.  
  
4. '''{{code|workshopNavModel}} "Browse" entry routes to a non-view action.''' The {{code|browse}} entry calls <code><nowiki>header.routeRequest("browse")</nowiki></code>, which triggers {{code|router.setRoute("browse")}}. {{code|Routes.browse}} has no {{code|qmlFile}} and no {{code|path}}, only {{code|action: "OPEN_STEAMWORKSHOP"}}. The router executes the action (opens the Steam overlay) and does not push a new view, leaving the header in the {{code|subnav-open}} state with the Workshop sub-nav still visible.  
  
5. '''{{code|mainNavBackgroundHeight}} is a redundant duplicate of {{code|mainNavHeight}}.''' Both are <code><nowiki>Math.ceil(64 * Theme.heightScale)</nowiki></code>. The TODO comment acknowledges this is a hack. A single property would suffice.  
  
6. '''{{code|checkButtonsActive()}} accesses {{code|campaignNavModel}} by hardcoded index.''' {{code|campaignNavModel.get(1)}} and {{code|campaignNavModel.get(2)}} are used directly. If the model order ever changes, the wrong entries will be toggled with no compile-time or runtime error.  
  
7. '''No {{code|id}} on the sub-nav {{code|ListView}}.''' The sub-nav list has no {{code|id}}, making it impossible to reference from outside the {{code|subNavContainer}} item (e.g. for programmatic scrolling or focus management).  
  
8. '''{{code|MainNavButton}} is registered in {{code|qmldir}} but is only used in {{code|component-header.qml}}.''' It is a thin wrapper over {{code|LetterboxButton}} with three property overrides. It could equivalently be an inline {{code|LetterboxButton}} with those properties set directly in the delegate.

====Notable issues====  
  
1. '''{{code|isControllerUsed}} is typed as {{code|int}} but used as a boolean.''' All four ternary expressions treat it as truthy/falsy. The property name implies a boolean, but the engine signal passes a navigation source type integer. If the engine ever passes a value of {{code|0}} for a controller source, the component will incorrectly display keyboard icons.  
  
2. '''No initial state query.''' There is no {{code|Component.onCompleted}} call to read the current navigation source from the engine. The component always starts in keyboard mode ({{code|isControllerUsed: 0}}) and only switches after the engine fires {{code|onNavigationSourceChanged}}. 3. '''{{code|rowSpacing}} has no effect.''' The {{code|GridLayout}} places all four groups in a single row (no wrapping), so {{code|rowSpacing}} — which controls vertical spacing between rows — is never applied.  
  
4. '''Redundant {{code|Column}} wrappers.''' Each of the four {{code|Column}} elements contains exactly one {{code|Row}} child. The {{code|Column}} adds no layout behaviour and could be replaced by the {{code|Row}} directly.  
  
5. '''{{code|containerWidth}} is 1024 logical pixels.''' At a 1920×1080 reference resolution this is 53% of the screen width. The {{code|Row}} in {{code|menuFooter}} does not clip its children, so on narrow resolutions or with long localized strings the guide may overlap the Quit and Back buttons to its left.  
  
6. '''Left padding inconsistency.''' Group 2 uses <code><nowiki>leftPadding: Math.ceil(18 * Theme.widthScale)</nowiki></code> while groups 1, 3, and 4 use <code><nowiki>Math.ceil(20 * Theme.widthScale)</nowiki></code>. The 2-pixel difference is not visually meaningful but is inconsistent.  
  
7. '''{{code|L10n.strings.navigation}} key values are not confirmed.''' The exact localization keys ({{code|#QTUI_*}} strings) backing {{code|change_tabs}}, {{code|options}}, {{code|discard}}, and {{code|select}} could not be read from {{code|l10n.qml}} within the available search results.

====Notable issues====  
  
1. '''{{code|reloadPageAfterApplyChanges}} is set to {{code|true}} after the reload.''' In the Apply button's {{code|onClicked}} handler, after calling {{code|router.setRoute(...)}}, the code immediately sets <code><nowiki>reloadPageAfterApplyChanges = true</nowiki></code>. This re-arms the flag after the reload has already been triggered, meaning the next Apply click will also reload the route even if {{code|reloadPageAfterApplyChanges}} was intended to be a one-shot flag. The assignment should be {{code|false}} or omitted.  
  
2. '''{{code|mat_savechanges}} is called N+1 times during {{code|flushPendingChanges()}}.''' {{code|_setValueImmediate}} calls {{command|mat_savechanges}} after every individual key write, and {{code|flushPendingChanges}} calls it again at the end. 3. '''{{code|router}} is accessed via implicit scope.''' {{code|flushPendingChanges()}} references {{code|router.currentRoute.name}} and {{code|router.setRoute(...)}} without declaring {{code|router}} as a property. This relies on QML's implicit scope chain resolving {{code|router}} to the {{code|Router}} id in {{code|main.qml}}. If {{code|OptionsList}} is ever used outside of {{code|main.qml}}'s scope tree, this will throw a ReferenceError.  
  
4. '''{{code|getComplex}}, {{code|setComplex}}, and {{code|groups}} are undeclared.''' The component accesses these as if they were properties, but they are not declared with {{code|property}} in the component definition. They are attached by consumers as child {{code|QtObject}} declarations. 5. '''{{code|keyNavigationEnabled: false}} on the {{code|ListView}}.''' Keyboard navigation between rows is handled externally by {{code|utils.qml}} via {{code|BlackMesaUtils.traverseUIElements()}}. The {{code|ListView}}'s built-in key navigation is disabled to prevent conflicts, but this means the list does not scroll automatically to keep the focused row visible when navigating with a controller or keyboard.  
  
6. '''{{code|inputWidth}} is a hardcoded formula.''' The input column width passed to each {{code|OptionsListRow}} is <code><nowiki>parent.width / 2 - (Theme.widthScale * 300)</nowiki></code>. This is not a named property and cannot be overridden per-consumer without modifying the delegate.

===component-optionslist-input-binding.qml===  
  
{{code|component-optionslist-input-binding.qml}} is the {{code|binding}} input type for the options list system. It renders two side-by-side {{code|BindingCell}} instances — one for the primary key binding and one for the secondary key binding — for a single engine command. It is loaded dynamically by {{code|component-optionslist-row.qml}} and is not registered in {{code|qmldir}}.  
  
====Registration and loading====  
  
The file is not registered in {{code|qmldir}}. It is referenced by name in {{code|component-optionslist-row.qml}}'s {{code|inputComponents}} registry:  
  
<pre>readonly property string binding: "component-optionslist-input-binding.qml"</pre>  
  
It is instantiated via a {{code|Loader}} when an {{code|OptionsListRow}} has <code><nowiki>model.type === "binding"</nowiki></code>. All {{code|binding}}-type rows are created exclusively by {{code|routeview-bindings.qml}}.  
  
====Root element====  
  
The root element is a {{code|FocusScope}} ({{code|id: root}}) with a single property:  
  
{| class="standard-table"  
! Property !! Type !! Description  
|-  
| {{code|model}} || {{code|variant}} || The binding row model object. Must contain {{code|command}}, {{code|key1}}, and {{code|key2}}.

Unlike all other input type components ({{code|slider}}, {{code|select}}, {{code|checkbox}}, {{code|map}}, {{code|text}}), the root {{code|FocusScope}} declares:  
* '''No''' {{code|objectName: "ui:option-item"}} — the {{code|BindingCell}} children carry this instead.  
* '''No''' <code><nowiki>readonly property string type: "binding"</nowiki></code> — the {{code|BindingCell}} children carry this instead.

* '''No''' {{code|selectedValue}} property.

The model object is produced by {{code|InputBindingsManager.getBindingComponentConfig()}} and populated by {{code|InputBindingsManager.getBindings()}}:  
  
{| class="standard-table"

| {{code|type}} || string || Always {{code|"binding"}}.

====requestSelection() function====  
  
<pre>function requestSelection(ordinal, begin, end)</pre>  
  
Called by each {{code|BindingCell}}'s {{code|onRequestInputSelection}} handler. It:  
  
* Manually copies all own properties of {{code|model}} into a new plain object {{code|cfg}} (using a {{code|for...in}} loop with {{code|hasOwnProperty}} guard, because Qt 5.9 lacks {{code|Object.assign}}).  
* Adds three extra fields to {{code|cfg}}:  
** {{code|ordinal}} — the string {{code|"key1"}} or {{code|"key2"}}, identifying which slot is being edited.  
** {{code|current}} — the current value of <code><nowiki>model[ordinal]</nowiki></code> (the key currently bound to that slot).  
** {{code|begin}} and {{code|end}} — screen coordinates passed up from {{code|BindingCell.requestInputSelection}}, used to position the conflict alert dialog.  
* Calls {{code|InputBindingsManager.selectBinding(cfg)}}, which sets {{code|InputBindingsManager.selectedCfg}} to {{code|cfg}} and triggers the key-capture flow in {{code|BindingCell}}.  
  
====Layout====  
  
The layout is a single {{code|Item}} ({{code|width: parent.width - 32}}) containing a {{code|Row}} ({{code|spacing: 0}}, {{code|anchors.fill: parent}}) with two {{code|BindingCell}} children:  
  
{| class="standard-table"  
! Element !! id !! Width !! Key property !! Selected condition  
|-  
| Primary cell || {{code|primary}} || <code><nowiki>parent.width / 2 + 16</nowiki></code> || {{code|model.key1}} || <code><nowiki>selectedCfg.ordinal === 'key1' && selectedCfg.command === model.command</nowiki></code>  
|-  
| Secondary cell || {{code|secondary}} || <code><nowiki>parent.width / 2 + 16</nowiki></code> || {{code|model.key2}} || <code><nowiki>selectedCfg.ordinal === 'key2' && selectedCfg.command === model.command</nowiki></code>  
|}  
  
Each cell's {{code|onRequestInputSelection}} handler calls {{code|requestSelection}} with the appropriate ordinal ({{code|'key1'}} or {{code|'key2'}}) and the {{code|begin}}/{{code|end}} coordinates from the signal.  
  
====Interaction with InputBindingsManager====  
  
When a {{code|BindingCell}} is clicked, it calls {{code|requestSelection}}, which calls {{code|InputBindingsManager.selectBinding(cfg)}}. This sets {{code|InputBindingsManager.selectedCfg}}, which the {{code|selected}} binding expressions on both cells observe reactively. The cell whose {{code|ordinal}} and {{code|command}} match {{code|selectedCfg}} transitions to the {{code|selected}} state in {{code|BindingCell}}, enabling key capture.  
  
When {{code|routeview-bindings.qml}}'s {{code|onRouteWillChange}} fires, it calls {{code|InputBindingsManager.clearSelection()}}, which sets {{code|selectedCfg}} to {{code|null}}, deselecting all cells.  
  
====Notable issues====  
  
1. '''Cell widths overflow the {{code|Row}}.''' The outer {{code|Item}} is <code><nowiki>parent.width - 32</nowiki></code> wide. The {{code|Row}} fills it, so {{code|Row.width [[=]] parent.width - 32}}. Each {{code|BindingCell}} is <code><nowiki>Row.width / 2 + 16 [[=]] parent.width / 2</nowiki></code> wide. The two cells together are {{code|parent.width}} wide, which is 32 pixels wider than the {{code|Row}}. The secondary cell overflows the right edge of the {{code|Item}} by 32 pixels. Since neither the {{code|Item}} nor the {{code|Row}} sets {{code|clip: true}}, this overflow is not clipped and the secondary cell visually extends beyond the intended boundary.  
  
2. '''No {{code|type}} property on the root.''' {{code|utils.qml}}'s keyboard/controller navigation dispatches Enter, Left, and Right key events by checking {{code|currentElement.type}}. Because the root {{code|FocusScope}} has no {{code|type}} property, the {{code|binding}} input type falls through all type checks in {{code|utils.qml}} and receives no keyboard navigation handling. The user cannot activate a binding cell via the controller Enter key from the row level; they must click directly on a {{code|BindingCell}}.  
  
3. '''Bypasses the {{code|requestSettingsChange}} signal chain.''' All other input types emit {{code|requestSettingsChange(model, value)}}, which propagates up through {{code|OptionsListRow}} → {{code|OptionsList}} → the route view's {{code|onRequestSettingsChange}} handler. Binding changes skip this entirely and call {{code|InputBindingsManager.selectBinding()}} directly. This means {{code|OptionsList}}'s pending-change tracking and {{code|flushPendingChanges()}} mechanism are never involved in binding operations.  
  
4. '''{{code|Object.assign}} workaround comment.''' The comment {{code|// qt 5.9 apparently lacks Object.assign}} documents a known engine limitation. The manual copy loop is correct but copies all enumerable own properties, including any QML-internal properties that {{code|hasOwnProperty}} returns {{code|true}} for on a {{code|ListElement}}-derived object. In practice this is harmless since {{code|InputBindingsManager}} only reads the known keys, but it is fragile.

====Interaction flow====  
  
The cell uses a deliberate two-click design to prevent accidental rebinds.  
  
=====Step 1: Selection (first click)=====  
  
Clicking the cell from {{code|blurred}} or {{code|focused}} calls {{code|makeSelectionRequest()}}, which emits {{code|requestInputSelection(beginBinding, endBinding)}}. The parent ({{code|component-optionslist-input-binding.qml}}) calls {{code|InputBindingsManager.selectBinding(cfg)}}, storing the config object (including the {{code|begin}} and {{code|end}} callbacks) in {{code|InputBindingsManager.selectedCfg}}. Because {{code|selected}} is a computed binding on {{code|selectedCfg}}, it becomes {{code|true}}, triggering {{code|onSelectedChanged}}, which sets {{code|clicker.state}} to {{code|"selected"}}.  
  
=====Step 2: Key capture (second click)=====  
  
Clicking the cell from {{code|selected}} calls {{code|startBinding()}}, which calls {{code|InputBindingsManager.startBindingRequest()}}. This function:  
  
# Calls {{code|clearSelection()}} (sets {{code|selectedCfg}} to {{code|null}}).  
# Calls {{code|cfg.begin()}} → {{code|beginBinding()}} → {{code|clicker.state}} becomes {{code|"binding"}}.  
# Calls {{code|BlackMesaEngine.requestKeyCapture()}} to begin listening for a key press.  
# Registers an {{code|inputBindingCallback}} closure that will handle the engine's response.  
  
=====Step 3: Key press or cancel=====  
  
When the engine captures a key, it emits {{code|onBindingResponse}} (handled in {{code|main.qml}}), which calls {{code|InputBindingsManager.handleBindingResponse(event)}}. The registered {{code|inputBindingCallback}} then:  
  
* '''ESC''' — calls {{code|cancel()}}: resets conflict state and calls {{code|cfg.end()}} with the original key, returning the cell to {{code|focused}} or {{code|blurred}}.  
* '''Any other key (no conflict)''' — calls {{code|execBindings()}}: issues {{code|unbind}} and {{code|bind}} console commands, saves via <code><nowiki>exec userconfig.cfg; host_writeconfig</nowiki></code>, calls {{code|cfg.end(event)}} → {{code|endBinding()}} → cell returns to {{code|focused}} or {{code|blurred}}, and emits {{code|bindingSet()}} to trigger a refresh.  
* '''Any other key (conflict)''' — if the key is already bound to a different command, {{code|InputBindingsManager.conflicts}} and {{code|InputBindingsManager.conflictCfg}} are set. {{code|cfg.end()}} is '''not''' called yet. {{code|routeview-bindings.qml}} watches {{code|conflicts}} and shows a conflict-resolution alert. The user can confirm (calls {{code|conflictCfg.confirm()}} → {{code|execBindings()}}) or cancel (calls {{code|conflictCfg.cancel()}} → {{code|cancel()}}).  
  
=====Hover during binding=====  
  
{{code|onEntered}} and {{code|onExited}} both guard against {{code|state [[=]][[=]][[=]] "binding"}} and {{code|state [[=]][[=]][[=]] "selected"}}, so hovering in or out during key capture or selection does not alter the state.  
  
====Usage====  
  
{{code|BindingCell}} is instantiated exclusively by {{code|component-optionslist-input-binding.qml}}, which creates two cells side by side — {{code|primary}} ({{code|key1}}) and {{code|secondary}} ({{code|key2}}) — each occupying half the row width. {{code|component-optionslist-input-binding.qml}} is in turn loaded dynamically by {{code|OptionsListRow}} when {{code|model.type}} is {{code|"binding"}}. {{code|component-binding.qml}} ({{code|BindingList}}) also uses {{code|OptionsListRow}} with {{code|binding}}-type models, so {{code|BindingCell}} is indirectly used there as well.  
  
====Notable issues====  
  
1. '''{{code|id: text}} conflicts with the {{code|text}} property.''' The {{code|Text}} element is given {{code|id: text}}, which shadows the {{code|text}} string property of the same element. Referencing {{code|text.text}} is valid QML but is confusing and error-prone.  
  
2. '''{{code|mouse.accepted}} references wrong parameter name.''' The {{code|onClicked}} handler is declared as <code><nowiki>onClicked: function(event) { ... }</nowiki></code>, naming the parameter {{code|event}}. The final line then writes {{code|mouse.accepted}} {{[[=]]}} {{code|true}}. Since the parameter is {{code|event}}, not {{code|mouse}}, this references {{code|MouseArea}}'s implicit {{code|mouse}} property (the last event object), not the current event. The assignment may silently succeed but does not reliably accept the current event.  
  
3. '''{{code|StateChangeScript}} in {{code|focused}} plays hover sound on every entry.''' This includes the transition from {{code|binding}} back to {{code|focused}} after a key is successfully bound, causing an unintentional hover sound to play at the end of every key-capture sequence.  
  
4. '''{{code|blurred}} ↔ {{code|focused}} transition only animates {{code|text}}.''' The background opacity change (0 → 0.2) is instant on hover, while the text color animates over 150 ms. All other transitions animate both {{code|text}} and {{code|background}} in parallel.  
  
5. '''{{code|selected}} ↔ {{code|binding}} is {{code|reversible: true}} but the reverse path is never used.''' {{code|endBinding()}} always sets state to {{code|focused}} or {{code|blurred}}, never back to {{code|selected}}. The {{code|binding}} → {{code|selected}} reverse transition is dead code. The separate explicit {{code|binding}} → {{code|focused}} transition is the one that actually fires.  
  
6. '''Conflict resolution leaves the cell in {{code|binding}} state.''' When a conflict is detected, {{code|cfg.end()}} is not called, so the cell remains in {{code|binding}} state (solid orange, key label hidden) while the conflict alert is displayed. If the user dismisses the alert without confirming or cancelling (which is not possible in the current UI but is not structurally prevented), the cell would be permanently stuck in {{code|binding}} state.

====Notable Issues====  
  
1. '''{{code|Theme.dimmedSlider}} typo in the {{code|"disabled"}} state.''' The {{code|PropertyChanges}} for the disabled state references {{code|Theme.dimmedSlider}} directly on the {{code|Theme}} singleton root, but the correct path is {{code|Theme.colors.dimmedSlider}}. Since {{code|Theme.dimmedSlider}} is {{code|undefined}}, the fill color in the disabled state will be {{code|undefined}}, which QML silently treats as transparent. The border color is correct ({{code|Theme.colors.dimmedText}}).  
  
2. '''{{code|onSelectedValueChanged}} is an empty no-op.''' The handler is declared but contains no logic. The {{code|selectedValue}} property is bound from {{code|model.value}} but is never read back by any internal logic — the component reads {{code|model.value}} directly for both the {{code|fill.visible}} condition and the toggle expression.  
  
3. '''Both left and right arrow keys produce identical behavior.''' Unlike {{code|"select"}} (left decrements, right increments) and {{code|"slider"}} (left decrements, right increments), the checkbox has no directional distinction. Pressing left or right both toggle the value. This is functionally correct for a binary toggle but is inconsistent with the directional model used by other input types.  
  
4. '''{{code|fill}} has conflicting anchor declarations.''' {{code|fill}} sets both {{code|anchors.fill: parent}} and {{code|anchors.centerIn: parent}}. In QML, {{code|anchors.fill}} and {{code|anchors.centerIn}} are mutually exclusive; setting both is an anchor conflict. QML will emit a warning at runtime and apply one set of anchors while ignoring the other. In practice {{code|anchors.fill}} takes effect (the fill covers the background minus margins), so the visual result is correct, but the conflict is a latent source of runtime warnings.  
  
5. '''Value is stored as a string, not a boolean.''' {{code|model.value}} is compared with the string literal {{code|'true'}} throughout. {{code|routeview-host.qml}} initialises the value via {{code|BlackMesaEngine.getConsoleVariableAsBoolean()}}, which presumably returns a string. If the engine ever returns a numeric {{code|"1"}} or {{code|"0"}} instead of {{code|"true"}} / {{code|"false"}}, the toggle logic and {{code|fill.visible}} condition will both silently fail.  
  
6. '''No hover sound at the component level.''' {{code|Sound.playEffect(Theme.sounds.buttonFocused)}} is not called inside this component. Hover feedback is provided by the parent {{code|OptionsListRow}}'s {{code|MouseArea.onEntered}}, which plays the focus sound for all non-separator row types. This is consistent with the other input widgets but means the checkbox itself has no independent hover feedback if used outside of {{code|OptionsListRow}}.

Unlike the {{code|select}} input type, which uses a QML {{code|ListModel}}, the {{code|map}} type expects {{code|model.options}} to be a '''plain JavaScript array''' of strings. ====Notable Issues====  
  
1. '''{{code|selectedValue}} is typed as {{code|bool}}.''' The property is declared {{code|property bool selectedValue}} but is bound to {{code|model.value}}, which is a map name string. QML will coerce the string to a boolean (non-empty string = {{code|true}}), making {{code|selectedValue}} always {{code|true}} for any valid map name. The property is effectively unused — {{code|onSelectedValueChanged}} is an empty handler.  
  
2. '''{{code|onSelectedValueChanged: {}}} is dead code.''' The handler is declared but empty. The component reacts to value changes only through the {{code|Binding}} element updating {{code|selectedValue}}, which triggers no meaningful logic.  
  
3. '''{{code|mapText.font.pixelSize: 12}} is hardcoded.''' The map name label uses a fixed pixel size not scaled by {{code|Theme.heightScale}} or {{code|Theme.widthScale}}, unlike every other text element in the options system. On high-resolution or non-1080p displays, the label will appear disproportionately small.  
  
4. '''{{code|mapText.text}} shows the raw BSP filename.''' The overlay displays the internal map filename (e.g. {{code|dm_stalkyard}}) rather than a human-readable display name. There is no lookup table or localization key for map display names.  
  
5. '''No keyboard or controller navigation.''' The component has no {{code|callback}} property and no {{code|Keys.onPressed}} handler. The {{code|select}} input type supports left/right key navigation via {{code|utils.qml}}'s {{code|navigationUIHandle}}; the {{code|map}} type does not. Controller and keyboard users cannot change the map selection.  
  
6. '''{{code|QtGraphicalEffects 1.0}} is imported but unused.''' No graphical effect (drop shadow, blur, colorize, etc.) is applied anywhere in the file. The import is a leftover.  
  
7. '''{{code|disabled}} state has no {{code|when:}} condition.''' The {{code|focused}} and {{code|blurred}} states use {{code|when: activeFocus}} / <code><nowiki>when: !activeFocus</nowiki></code> and are reactive. The {{code|disabled}} state has no {{code|when:}} and must be set via the initial property passed from {{code|component-optionslist-row.qml}}. If the row's disabled status changes after the loader completes, the map input's state will not update.  
  
8. '''Wrapping behavior differs from {{code|select}}.''' The {{code|select}} input hides the left arrow at index 0 and the right arrow at the last index, preventing wrap-around. The {{code|map}} input wraps silently in both directions with no visual indication that the list is circular.  
  
9. '''Sole consumer is {{code|routeview-host.qml}}.''' The {{code|map}} input type is used in exactly one {{code|OptionsListRow}} in the entire codebase. The {{code|routeview-join.qml}} server browser does not use it; map names in the join view are plain data fields in the server list, not interactive inputs.

====Quirks and Issues====  
  
1. '''{{code|tabsContainer}} is hidden for exactly two options.''' The tab strip is only shown when <code><nowiki>model.options.count > 2</nowiki></code>. Binary selects (e.g. On/Off toggles) show no position indicator at all — only the arrows convey position, and those disappear at the boundary indices. A user at index 0 of a two-option select sees only the right arrow with no indication that there is a second option.  
  
2. '''{{code|anchors.verticalCenterOffset}} is always −2 when options exist.''' The offset is <code><nowiki>model.options.count ? -2 : 0</nowiki></code>, so it applies even for two-option selects where {{code|tabsContainer}} is invisible. The label is shifted upward for no visual reason in those cases.  
  
3. '''{{code|tabsContainer.anchors.rightMargin}} has no effect.''' The container is anchored on its left side to {{code|leftArrow.right}} and has no right anchor, so {{code|anchors.rightMargin: triangleButtonWidth/2}} is silently ignored by the QML layout engine.  
  
4. '''{{code|rightArrow.anchors.leftMargin}} has no effect.''' {{code|rightArrow}} is anchored to {{code|parent.right}}, not to a left anchor, so {{code|anchors.leftMargin: triangleButtonWidth/2}} is silently ignored.  
  
5. '''{{code|warningSign}} uses integer comparison instead of boolean.''' <code><nowiki>model.options.get(selectedIndex).warning ? 1 : 0</nowiki></code> converts the result to an integer before assigning to {{code|visible}}, which expects a boolean. QML coerces non-zero integers to {{code|true}}, so this works, but it is inconsistent with the boolean {{code|visible}} convention used everywhere else.  
  
6. '''{{code|updateHeaderWarningVisibility}} is resolved via dynamic scope.''' The call relies on the QML property lookup chain finding {{code|updateHeaderWarningVisibility}} in an ancestor scope (specifically {{code|routeview-video.qml}}'s {{code|OptionsList}}). This is fragile: if the component is ever used in a context where that function is not in scope, the {{code|typeof}} guard silently suppresses the call with no warning.  
  
7. '''Arrow {{code|opacity}} and {{code|visible}} are independently controlled.''' {{code|visible}} is tied to the index boundary; {{code|opacity}} is tied to {{code|enabled}}. A disabled select at a non-boundary index will show a fully transparent (but still layout-occupying) arrow. The {{code|Behavior on opacity}} animates the fade, but since {{code|visible}} is not animated, the arrow disappears instantly when the index reaches a boundary even if the opacity animation is mid-flight.  
  
8. '''Click sound is played inside the select component, not the row.''' Both {{code|leftArrow.onClicked}} and {{code|rightArrow.onClicked}} call {{code|Sound.playEffect(Theme.sounds.buttonClicked)}} directly. The hover sound ({{code|Theme.sounds.buttonFocused}}) is played by {{code|component-optionslist-row.qml}}'s {{code|MouseArea.onEntered}}, creating an asymmetry where hover and click sounds originate from different components.  
  
9. '''No wrapping.''' Clicking the left arrow at index 0 or the right arrow at the last index is prevented by hiding the respective arrow, but there is no wrap-around option. Keyboard/controller left-right navigation (handled by {{code|utils.qml}}) also does not wrap.

====Notable Issues====  
  
1. '''{{code|sliderWidthPadding}} is a dead property.''' It is defined as <code><nowiki>Math.ceil(60 * Theme.widthScale)</nowiki></code> but is never referenced anywhere in the file. The actual horizontal inset is controlled by {{code|sliderMargin}}.  
  
2. '''{{code|handleWidth}} uses {{code|Theme.heightScale}}.''' The handle width is <code><nowiki>Math.ceil(15 * Theme.heightScale)</nowiki></code> instead of {{code|Theme.widthScale}}. On non-16:9 displays where the two scales differ, the handle will be proportionally wider or narrower than intended, and the drag range calculation (<code><nowiki>drag.maximumX: parent.width - handleWidth</nowiki></code>) will be slightly off.  
  
3. '''Step snapping always rounds down.''' {{code|coordsToValue}} uses <code><nowiki>Math.floor(outval / stepValue) * stepValue</nowiki></code>. This always snaps to the lower step rather than the nearest step. A drag position that maps to 0.159 with {{code|stepValue: 0.1}} will snap to 0.1 rather than 0.2.  
  
4. '''{{code|onClicked}} redundantly sets state manually.''' The {{code|focused}} and {{code|blurred}} states already have {{code|when:}} conditions bound to {{code|sliderInput.activeFocus}}. The explicit <code><nowiki>sliderInput.state = "focused"</nowiki></code> in {{code|onClicked}} is redundant and can conflict with the declarative state binding.  
  
5. '''{{code|valueText}} left margin is unscaled.''' {{code|anchors.leftMargin: 8}} is a hardcoded pixel value not multiplied by {{code|Theme.widthScale}}, unlike every other margin in the file.  
  
6. '''{{code|whole}} formatter is unused.''' No slider row in any route view specifies <code><nowiki>formatter: "whole"</nowiki></code>. The function is dead code.  
  
7. '''{{code|disabled}} state hides the handle but not the track fill.''' When disabled, {{code|sliderHandle.opacity}} is set to {{code|0}} (invisible), but {{code|sliderHighlight}} remains visible with {{code|Theme.colors.dimmedSlider}} colour. The track fill still shows the current value position even though the control cannot be interacted with.  
  
8. '''{{code|onReleased}} applies {{code|toFixed}} after step snapping.''' The call chain is <code><nowiki>coordsToValue(coords).toFixed(model.precision)</nowiki></code>. Since {{code|coordsToValue}} already snaps to {{code|stepValue}}, the {{code|toFixed}} call only affects string formatting, not the stored value. However, if {{code|model.precision}} is less than the number of significant digits in {{code|stepValue}}, the stored string will be rounded differently from the snapped value (e.g. {{code|stepValue: 0.010000}}, {{code|precision: 2}} → value {{code|0.01}} stored as {{code|"0.01"}}, which is correct, but {{code|stepValue: 0.001}}, {{code|precision: 1}} → value {{code|0.123}} stored as {{code|"0.1"}}, discarding precision).

====Notable Issues====  
  
1. '''{{code|selectedValue}} is declared as {{code|bool}}.''' The property type should be {{code|string}} (or {{code|variant}}) to match the string values stored in text-type model entries. As declared, QML will coerce {{code|model.value}} to a boolean, making {{code|selectedValue}} useless as a string mirror of the current value.  
  
2. '''{{code|onSelectedValueChanged}} is commented out.''' The handler is present but disabled (<code><nowiki>//    onSelectedValueChanged: {}</nowiki></code>). As a result, if {{code|model.value}} changes externally after the component is loaded, {{code|textField.text}} is not updated — it retains the value set at construction time via the {{code|text: model.value}} binding. Note that {{code|text: model.value}} is a one-time assignment in {{code|QtQuick.Controls 2.2}} once the user edits the field, so external model updates are silently dropped.  
  
3. '''{{code|requestSettingsChange}} fires on every keystroke.''' There is no debounce, no {{code|onEditingFinished}}, and no {{code|onAccepted}} handler. Every character typed immediately triggers a {{code|setConsoleVariable}} call through the signal chain, which may cause excessive engine writes for long strings.  
  
4. '''Malformed {{code|Behavior}} block.''' The {{code|Behavior { ColorAnimation { duration: 75 } } }} declaration inside {{code|textField}} is missing the mandatory <code><nowiki>on color</nowiki></code> clause. The QML engine ignores it, so the intended 75 ms color animation on focus/blur transitions does not occur.  
  
5. '''Unused {{code|QtQuick.Controls.Styles 1.4}} import.''' This is the Qt Quick Controls 1 styling API, which is incompatible with the {{code|QtQuick.Controls 2.2}} {{code|TextField}} used in the same file. The import is a leftover and has no effect.  
  
6. '''No {{code|placeholderText}}.''' An empty text field gives no visual hint about the expected input. All other text-type rows in {{code|routeview-host.qml}} rely on the label column for context, but the field itself provides no in-field guidance.  
  
7. '''{{code|background}} uses {{code|Theme.colors.modalBackground}}.''' The background color ({{code|#222222}}) is the same dark tone used for modal dialog backgrounds, not the standard options list row background. This is visually consistent with the dark UI aesthetic but is semantically mismatched — the field background is not a modal.

====Notable Issues====  
  
1. '''{{code|headerFontSize}} and {{code|headerMargin}} are unresolved in standalone use.''' The {{code|separator}} branch in {{code|labelText.Component.onCompleted}} references {{code|headerFontSize}} and {{code|headerMargin}}, which are not declared in {{code|component-optionslist-row.qml}}. They are resolved via QML's dynamic scope from the parent {{code|component-optionslist.qml}} (where they are defined as {{code|Math.ceil(32 * Theme.heightScale)}} and {{code|Math.ceil(35 * Theme.widthScale)}} respectively). When {{code|OptionsListRow}} is used directly — as in {{code|routeview-host.qml}} — these identifiers are {{code|undefined}}, and the separator formatting silently fails.  
  
2. '''{{code|onSelectionChanged}} and {{code|updateHeaderWarningVisibility}} are dynamic-scope calls.''' Neither function is declared in the component. They are resolved at runtime from the enclosing scope. If the row is used outside a context that provides these functions, the {{code|typeof}} guard prevents a crash, but the behavior is silently absent.  
  
3. '''{{code|inputWidth}} is a dead property.''' {{code|component-optionslist.qml}} passes {{code|inputWidth}} to the row via {{code|setSource}}, but {{code|component-optionslist-row.qml}} never declares or uses it. The loader width is hardcoded as <code><nowiki>(parent.width / 2) - (128 * Theme.widthScale)</nowiki></code>.  
  
4. '''State conflict on slider and select sub-components.''' The slider and select input types declare {{code|when}} conditions on their states (e.g. <code><nowiki>when: sliderInput.activeFocus</nowiki></code>), which causes QML to manage their state automatically. The row's {{code|Binding}} also writes to {{code|loader.item.state}}. These two mechanisms compete: the {{code|when}} condition takes precedence in QML's state evaluation, so the {{code|Binding}} may be silently overridden.  
  
5. '''{{code|binding}} type does not emit {{code|requestSettingsChange}}.''' {{code|component-optionslist-input-binding.qml}} has no {{code|requestSettingsChange}} signal. The {{code|onLoaded}} handler in the row attempts to connect it unconditionally via <code><nowiki>item.requestSettingsChange && item.requestSettingsChange.connect(...)</nowiki></code>, which is safe due to the guard, but means binding changes bypass the {{code|OptionsList}} settings pipeline entirely and go directly to {{code|InputBindingsManager}}.  
  
6. '''{{code|checkbox}} disabled state references {{code|Theme.dimmedSlider}} instead of {{code|Theme.colors.dimmedSlider}}.''' The {{code|disabled}} state in {{code|component-optionslist-input-checkbox.qml}} sets <code><nowiki>fill.color: Theme.dimmedSlider</nowiki></code>, omitting the {{code|.colors}} qualifier. {{code|Theme.dimmedSlider}} does not exist; the property resolves to {{code|undefined}}, leaving the fill color unchanged when the checkbox is disabled.  
  
7. '''{{code|map}} type uses a hardcoded {{code|font.pixelSize: 12}}.''' The map name label inside the thumbnail overlay uses a fixed pixel size not scaled by {{code|Theme.heightScale}} or {{code|Theme.widthScale}}, unlike every other text element in the options system.  
  
8. '''{{code|text}} type imports the deprecated {{code|QtQuick.Controls.Styles 1.4}}.''' This module is not used anywhere in the file; the import is a leftover. {{code|QtQuick.Controls.Styles}} is the Qt 5 Quick Controls 1 styling API and is incompatible with the {{code|QtQuick.Controls 2.2}} {{code|TextField}} used in the same file.  
  
9. '''{{code|separator}} input component is an empty stub.''' {{code|component-optionslist-input-separator.qml}} contains only an empty {{code|Item}} and a TODO comment suggesting a horizontal line or similar visual. No separator decoration is rendered on the right side of separator rows.

2. '''{{code|scrollbarDimension}} uses {{code|Theme.widthScale}} for both axes.''' On non-16:9 displays where {{code|widthScale}} and {{code|heightScale}} differ, the thumb minimum height will be proportionally incorrect relative to the vertical axis.  
  
3. '''No track background.''' The {{code|background}} property of the {{code|ScrollBar}} is not overridden, leaving the track area transparent. The scrollbar thumb floats over the list content with no visual track indicator, which can make it difficult to perceive the scrollable range.  
  
4. '''{{code|stepSize: 0.02}} is content-length-agnostic.''' A fixed 2% step means that on a list with 5 items, one scroll step moves ~0.1 items; on a list with 100 items, one step moves ~2 items. There is no adaptive step size based on visible row count.  
  
5. '''{{code|routeview-achievements.qml}} hardcodes {{code|visible: true}}.''' This is identical to the base class default and provides no conditional logic. The scrollbar is always shown on the achievements page even if all achievements fit within the page height, which is possible for games with very few achievements.

Maps 19 background keys ({{code|background01}} through {{code|background19}}) to VTF image URLs under {{code|image://game/materials/console/}}. Each key has a standard variant and a {{code|_widescreen}} variant, giving 38 entries total.  
  
=====_maps=====  
  
Maps source strings to background keys. For the 19 numbered backgrounds the mapping is trivially 1-1 ({{code|background01}} → {{code|'background01'}}, etc.). Four additional entries map specific BSP map names to background keys for use during inter-chapter loads:

| {{code|bm_c1a0a}}  
| {{code|background02}}

A TODO comment in the source notes that only four map-name aliases exist and that the mapping is incomplete.  
  
====Functions====  
  
=====updateBackgroundImage(mapname)=====  
  
Public. Called by {{code|main.qml}} from {{code|onWidthChanged}} and {{code|onHeightChanged}} (without an argument, to recompute widescreen selection on resize), and from {{code|routeview-video.qml}} after a resolution change.  
  
If {{code|mapname}} is provided, it is stored in {{code|_mapname}}. The function then calls {{code|_getUrl(_mapname, widescreen)}} where the widescreen flag is <code><nowiki>appRoot.width / appRoot.height >= 1.586</nowiki></code> (approximately a 16:10 aspect ratio threshold). If the resolved URL differs from the current {{code|backgroundImageUrl}}, it is assigned, triggering the 1250 ms fade animation (unless {{code|suppressAnimations}} is {{code|true}}).  
  
=====_getUrl(mapname, widescreen)=====  
  
Private. Looks up {{code|_maps[mapname]}} to get a background key, appends {{code|'_widescreen'}} if {{code|widescreen}} is {{code|true}}, then returns {{code|_files[key]}}. Returns {{code|undefined}} if {{code|mapname}} is not in {{code|_maps}}.  
  
====Visual Children====  
  
=====backgroundImage=====  
  
An {{code|Image}} that fills the parent. Its {{code|opacity}} is {{code|1.0}} when {{code|showImage}} is {{code|true}} and {{code|0.0}} otherwise, animated over 1250 ms. The {{code|source}} is controlled via the {{code|backgroundImageUrl}} alias.  
  
=====bottomLeftMesaLogo=====  
  
An {{code|Image}} displaying {{code|ui/images/logo-mark.png}}, anchored to the bottom-right corner of the parent with zero margin. Width and height are both <code><nowiki>Math.ceil(750 * Theme.widthScale)</nowiki></code> (750×738 native pixels). This element has no opacity control and is always visible regardless of any property flags.  
  
=====subBackgroundGradient=====  
  
A {{code|Rectangle}} rotated −90° around its top-left corner, producing a vertical gradient that runs from bottom to top of the screen. The gradient goes from {{code|subNavBackground}} (first stop, position 0.0) to {{code|transparent}} (position 1.0). Opacity is {{code|0.7}} when {{code|showExtras}} is {{code|true}}, otherwise {{code|0.0}}, animated over 1250 ms.  
  
=====backgroundGradient=====  
  
Identical rotation and sizing to {{code|subBackgroundGradient}}. The gradient goes from {{code|Theme.colors.highlight}} ({{code|#e47125}}, orange) at position 0.0 to {{code|transparent}} at position 1.0. Opacity is {{code|0.15}} when {{code|showExtras}} is {{code|true}}, otherwise {{code|0.0}}, animated over 1250 ms.  
  
=====skrim=====  
  
A {{code|Rectangle}} filling the parent with color {{code|Theme.colors.skrim}} ({{code|#2d2d2d}}). Opacity is {{code|_skrimOpacity}} when {{code|showSkrim}} is {{code|true}}, otherwise {{code|0.0}}, animated over 600 ms (shorter than the image/gradient animations).

====Notable Issues====  
  
1. '''{{code|subNavBackground}} is an unqualified identifier.''' On line 147, the first {{code|GradientStop}} of {{code|subBackgroundGradient}} uses {{code|subNavBackground}} as its color value without the {{code|Theme.colors.}} prefix. {{code|subNavBackground}} is not defined anywhere in the component's scope or any ancestor scope. At runtime this resolves to {{code|undefined}}, and QML will silently substitute a default color (typically black or transparent), making the gradient visually incorrect. The correct reference is {{code|Theme.colors.subNavBackground}} ({{code|#111111}}).  
  
2. '''{{code|showExtras}} is never set to {{code|true}}.''' The {{code|main.qml}} instantiation does not bind {{code|showExtras}}, and no other file in the codebase sets it. Both gradient overlays ({{code|subBackgroundGradient}} and {{code|backgroundGradient}}) are permanently invisible at runtime.  
  
3. '''Widescreen VTF mismatches in {{code|_files}}.''' Several widescreen keys point to the wrong VTF file:

These appear to be copy-paste or off-by-one errors. {{code|background12_widescreen}} correctly maps to {{code|background12_widescreen.vtf}}, so the sequence resumes correctly from key 12 onward.  
  
4. '''{{code|_mapname}} starts empty.''' On construction, {{code|_mapname}} is {{code|""}}. If {{code|updateBackgroundImage()}} is called without an argument before any map name has been provided (e.g. on the first {{code|onWidthChanged}} event), {{code|_getUrl("", ...)}} returns {{code|undefined}} and {{code|backgroundImageUrl}} is not updated. The background image remains unset until a map name is supplied.  
  
5. '''{{code|bottomLeftMesaLogo}} uses {{code|Theme.widthScale}} for both dimensions.''' The height is <code><nowiki>Math.ceil(750 * Theme.widthScale)</nowiki></code> rather than <code><nowiki>Math.ceil(738 * Theme.heightScale)</nowiki></code>. This preserves the aspect ratio of the logo relative to screen width, but the logo will appear slightly distorted on non-16:9 displays where {{code|widthScale}} and {{code|heightScale}} differ.  
  
6. '''{{code|_maps}} 1-1 section is redundant.''' The TODO comment expresses a desire for a 1-1 mapping between map names and background filenames. The 19 numbered entries in {{code|_maps}} already are 1-1 ({{code|background01}} → {{code|'background01'}}), making the entire {{code|_maps}} lookup unnecessary for those keys — {{code|_files[mapname]}} would produce the same result directly. Only the four BSP map name aliases at the bottom justify the indirection.
